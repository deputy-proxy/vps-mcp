# Persistent project environments

## Purpose and boundaries

A project environment is the durable development application environment for one registered repository. It is not a task workspace, task sandbox, repository bare cache, or production deployment. Its only source branch is `development`; `main` and task feature branches are never deployment sources.

The project-environment manager owns application checkout/release state, service profiles, project-specific data directories, deployment history, health state, backup metadata, and lifecycle reconciliation. The rootless runtime remains the only component allowed to create and control containers. The public MCP process communicates with it through the typed runtime adapter and never receives Podman access.

## Identity and durable state

The canonical identity is the immutable managed repository ID. There is at most one environment record per repository ID. Records are stored beneath `$MCP_DATA_DIR/project-environments/<repository-id>/environment.json` with directory mode 0700 and file mode 0600. Writes use a same-directory temporary file, fsync where supported, and atomic rename. A cross-process repository-scoped lock serializes lifecycle and deployment mutations.

The record contains only non-secret metadata: schema version, repository ID/full name, source branch (the literal `development`), environment root, active and candidate release IDs, profile identifier/version, desired and observed lifecycle state, workload IDs, resource vector, health summary, deployment/backup history references, timestamps, and last reconciliation result. Credentials and environment variable values are never persisted in this record or logs.

Environment-owned data is separated by purpose: immutable release checkouts, shared project database data, uploads/storage, cache, logs, backups, and generated runtime configuration. Each repository receives distinct paths, database/schema and credentials, cache namespace, and service identity. Production data, credentials, storage and mounts are explicitly forbidden.

## Source and release model

The source is the registered repository's canonical Git remote and the `development` branch only. The manager fetches the bare repository cache, resolves the remote-tracking `development` commit, and creates a new immutable release checkout. It never checks out `main`, task branches, caller-provided refs, or arbitrary repository URLs.

A deployment follows prepare, validate, activate, verify, and commit phases. Build and dependency installation occur in a candidate release, not in the active checkout. Activation switches an environment-owned release pointer atomically. Health checks must pass before the candidate becomes the recorded active release. On failure, restore the previous pointer and preserve the failed release and sanitized diagnostics for investigation. Do not mutate an active release in place.

## Service profiles

The core model is profile-driven and framework-neutral. A versioned profile defines its runtime/toolchain, immutable image digest, web process, optional queue workers and scheduler, health checks, ports, resource defaults, persistent mount declarations, startup/restart policy, database/cache requirements, build and release hooks, migration/seeder policy, and backup/restore requirements.

The profile catalog is exposed through project-environment.profile.list. Profile IDs and versions are immutable contracts: changing behavior requires a new profile version. Callers receive copies of profile definitions; they cannot mutate the in-process catalog.

Laravel/PHP is the first profile family. Versions 1–3 remain immutable historical contracts. Version 4 is the current dependency-stack contract: PHP-FPM plus required MySQL 8.4.13 and optional Redis 8.10.3. The PHP runtime and both dependency images are pinned by immutable SHA-256 digests. Redis is disabled by default and is enabled explicitly at environment registration. Queue workers and the scheduler remain disabled until multi-process project-service supervision is implemented.

Version 4 declares MySQL as required and Redis as optional. The environment registry schema v2 records the enabled dependency selection and migrates schema-v1 records without changing environment IDs, release identities, persistent paths or resource reservations. New environments reserve the PHP-FPM vector plus only the selected dependency vectors; migrated environments preserve their previous aggregate reservations. A dependency selection is immutable after registration. The profile remains definition-only until its complete runtime image manifest is administratively promoted and disposable-project acceptance is completed.

The Laravel profile's storage and logs mounts are intentionally nested: the project storage bind is mounted first at `/app/storage`, then the isolated logs bind overlays `/app/storage/logs`. The cache mount is separate at `/app/bootstrap/cache`. The profile validator permits only this explicit storage/logs nesting and rejects duplicate targets or any other nested mount relationship. The runtime stages each source independently through the quota broker and verifies its repository/workload identity and mount options.

The runtime mount verifier resolves the mounted source against every canonical root in VPS_SANDBOX_PROJECT_ENV_ROOTS_JSON, not only the legacy single-root setting. Each configured root has a dedicated owner; the privileged quota broker selects the one root containing the repository and rejects missing or duplicate repository identities. The runtime accepts a mount only when its source matches exactly one configured root plus the expected repository, release and data path. The legacy VPS_SANDBOX_PROJECT_ENV_ROOT / VPS_SANDBOX_PROJECT_ENV_OWNER pair remains supported when no root map is configured.

The Laravel runtime image is built from digest-pinned PHP-FPM, Composer and Node.js upstream images. Its build and smoke-test contract lives in `runtime/laravel-php/`; CI scans the resulting image and publishes development builds with SBOM and provenance attestations. A published digest is not automatically sufficient to enable a project profile: the exact digest, runtime acceptance and project-service isolation/lifecycle evidence must all pass before a profile is marked deployable.

## Isolation and resource admission

Environment registration reserves CPU, memory, PIDs and disk through the #36 `resource.reserve` operation for the registered repository ID. The requested vector is the aggregate of the profile's PHP application vector plus every declared dependency vector (with explicitly supplied bounded overrides that cannot reduce any dimension below the profile's aggregate workload requirements) and must fit both global and per-repository budgets plus the host disk safety margin. A reservation failure leaves the metadata record visible with a recorded error and no service may be provisioned; retrying registration retries the idempotent reservation. An identical reservation request is a no-op even while the project service is running. A changed reservation is rejected while project-service workloads are active. Each persistent project workload consumes its portion of the aggregate reservation rather than being charged twice. The PHP-FPM workload persists both its own effective resource vector and the aggregate reservation identity. Resource governance accounts dependency workloads, including stopped instances, in the same project envelope. Reservations are released only after the environment and all project workloads have been deprovisioned.

Each project gets private configuration, database/schema and credentials, storage/uploads, cache namespace and logs. Runtime mounts are explicit and project-scoped. Project services do not inherit task workspace mounts, task execution-log mounts, task egress proxy access, or task sandbox credentials. The project-service runtime creates a deterministic repository-specific Podman pod with `--network=none` and shares only its network namespace (`--share=net`) with project members. The pod uses its own infra container, no host network, and no published ports. The pod infra container may restart with the pod, but application and dependency containers use `restart=no`; the runtime recovery controller is the only component that starts them, preserving MySQL → Redis → PHP-FPM ordering after reboot. PHP-FPM, MySQL and optional Redis join this same loopback-only namespace. The application connects to MySQL and Redis through `127.0.0.1`; separate repositories receive separate pods, data directories and credentials. Dependency workload identities include repository, environment and dependency name. A task sandbox uses a separate worktree and cannot mount or write any persistent project path.

Project-service start is not considered successful until the runtime verifies the declared PHP-FPM TCP health check at 127.0.0.1:9000 from inside the container as the non-root application user. The runtime retries within a bounded startup window and stops the project pod if health never becomes ready. Runtime inspection refreshes the persisted health observation; stopped or missing workloads are not reported as healthy.

## Lifecycle and recovery

Desired states are `provisioned`, `running`, `stopped`, and `deprovisioned`; observed states additionally include `starting`, `stopping`, `degraded`, `unknown`, and `error`. Mutations persist intent before calling the runtime and persist the observed result afterward. Operations are idempotent and keyed by stable environment/workload identity.

MCP startup and host reboot recovery reconcile environment records against runtime workload records. Persistent services use an explicit restart policy. Missing, unregistered, or identity-mismatched containers are not silently deleted or recreated; they produce an actionable degraded/unknown result. Task cleanup and ephemeral reaping must never stop, remove, or delete project environments, releases, databases, uploads, backups, or logs.

## Backups, migrations and rollback

Database migrations run only against the project's development database and only as part of a controlled deployment. Seeders are disabled by default and require an explicit profile-level allowlist; production targets are impossible by construction. Backups include database and project-owned persistent files, carry repository/environment identity and checksums, and are written outside the live data directories. Restore validates identity and backup integrity before replacing data. It extracts into a hidden staging directory inside the existing storage mount, then swaps directory contents while preserving the storage mount inode; a safety backup supports rollback without remounting a live container namespace.

A deployment rollback restores the prior immutable release and compatible runtime configuration. Data rollback is separate and requires an explicit restore operation; a code rollback must not silently roll back database data.

## Delivery gates

Do not enable broad onboarding or live provisioning until resource governance (#36) is accepted and the project-service runtime contract is verified. Host-level changes, service installation, reverse-proxy exposure, DNS and production-adjacent operations require explicit review and approval. All tests use disposable repositories and isolated development-only data.

## Dependency workload contract

A Laravel v4 environment uses one deterministic workload ID per enabled dependency. The runtime stores dependency records as `project-dependency` workloads and the application record stores the owning environment ID plus the exact dependency workload IDs. MySQL starts before Redis, and both are verified before PHP-FPM starts. A service start never starts the Podman pod as a whole: it starts the pod infra container, starts and verifies MySQL, starts and verifies Redis when enabled, then starts PHP-FPM. Stop order is PHP-FPM, Redis, MySQL. Deprovision removes the application and dependency containers before releasing the aggregate reservation; database, storage and backups remain on disk.

MySQL uses the approved DHI MySQL 8.4.13 image and a per-environment root credential file plus a separate application credential. The initialization script creates only the `app` database and an application user granted privileges only on `app.*`. It does not rely on unsupported `MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_PASSWORD` or init-directory behavior in the selected DHI image. Redis uses the approved DHI Redis 8.10.3 image, a per-environment ACL user, a protected ACL file and a 64 MiB tmpfs data directory. Redis is cache-only and ephemeral: persistence and Redis backup are intentionally disabled. The PHP runtime receives its database and Redis configuration through a generated, read-only runtime `.env` mount; credentials are not passed as process arguments or persisted in environment metadata.

Dependency containers use read-only root filesystems, non-root image users, bounded CPU/memory/PID resources, no published ports, no host networking, and only their own data/secret file mounts. MySQL receives only its root password file and client config; Redis receives only its ACL and server config. The Redis application password remains host-side for authenticated health probes and is sent to `redis-cli` over stdin, never through arguments or environment variables. MySQL data is persistent at the environment database path. Redis data is ephemeral tmpfs. Secret directories and files are root-owned with restrictive permissions and are mounted read-only. Secret values never appear in tool responses, audit events or runtime logs. Secret preparation is idempotent and fails closed if existing credential files and generated runtime configuration disagree.

Resource governance accounts PHP-FPM and every enabled dependency against the same aggregate reservation, including stopped workloads. The runtime verifies container identity, pod membership, mount identity and effective cgroup v2 limits. Cleanup and task lifecycle operations cannot target project dependencies. Recovery follows the parent application desired state: a stopped/deprovisioning application causes its dependencies to stop; a running application causes dependencies to be started and verified before PHP-FPM. Missing or identity-mismatched workloads remain visible for operator review.

## Encrypted backup and restore contract

`project-environment.backup` creates an AES-256-GCM encrypted backup of the MySQL logical database and project storage. The application is briefly stopped to quiesce storage writes while MySQL remains available for a single-transaction logical dump. Each artifact is bounded to 256 MiB. A per-environment 256-bit key is stored in a protected root-owned secret directory and is never returned to MCP callers. The manifest is authenticated with HMAC-SHA-256 and records repository ID, environment ID, profile ID/version, enabled dependency selection, artifact filenames, checksums, sizes, nonces and authentication tags. Redis is excluded because it is explicitly ephemeral cache.

`project-environment.restore` requires explicit confirmation and an exact repository/environment/profile/dependency match. It validates the manifest HMAC and both encrypted artifact checksums before changing data, creates a fresh encrypted safety backup, restores MySQL and stages storage replacement, verifies application health, and rolls back the database and storage on failure. Backups are stored in the environment's protected local backups directory; this implementation does not replicate them off-host. Deprovisioning preserves backups and persistent data.
